# Модель угроз системы персональных данных

## Объём и допущения

Модель охватывает публичные формы, первичные JSON-заявки, карантин, consent-audit, PM2/Nginx, архитектурный фундамент SQLite и будущую закрытую административную часть. Production-состояние VPS проверяется вручную: локальный код не доказывает настройки firewall, права каталогов или резервного копирования.

### Активы

- контактные и технические данные в заявках;
- чертежи и вложения;
- доказательства согласий;
- служебные комментарии, обращения субъектов и сведения об инцидентах;
- учётные записи, сессии и секреты;
- официальные выгрузки и резервные копии;
- целостность журналов доступа и удаления;
- непрерывность приёма заявок.

### Границы доверия

1. Интернет → Nginx.
2. Nginx → Next.js на loopback.
3. Next.js → непубличное файловое хранилище.
4. Индексатор → SQLite.
5. Уполномоченный сотрудник → внутренняя система.
6. Система → временный экспорт или backup.

## Реестр угроз

| Угроза | Актив и сценарий | Вероятность | Ущерб | Существующая мера | Требуемая мера | Остаточный риск |
|---|---|---:|---:|---|---|---|
| Прямой доступ к Node.js | Запрос к IP:3000 обходит Nginx и позволяет подменять proxy headers | Высокая до ручного исправления | Высокий | PM2-конфигурация подготовлена для loopback | Подтвердить `127.0.0.1`, закрыть 3000 firewall и извне | Низкий после двух уровней защиты |
| Подмена proxy headers | Клиент влияет на IP-идентификацию при прямом доступе | Высокая до закрытия 3000 | Высокий | Приложение доверяет proxy только по флагу | Включать `TRUST_NGINX_PROXY` лишь при loopback и firewall | Низкий |
| Компрометация учётной записи | Злоумышленник получает пароль сотрудника | Средняя | Критический | Versioned scrypt, индивидуальная соль, роли | MFA на следующем этапе, step-up, уведомления, отзыв сессий | Средний до MFA |
| Перебор паролей | Массовые попытки входа по имени/IP | Средняя | Высокий | Таблица попыток, блокировка пользователя и IP hash | Серверный endpoint обязан применять единый login policy; мониторинг | Низкий–средний |
| Кража session cookie | Вредоносный код/устройство использует сессию | Средняя | Высокий | `__Host-`, HttpOnly, Secure, SameSite=Strict, idle/absolute TTL | CSP, TLS, отзыв всех сессий, step-up для опасных действий | Средний |
| CSRF | Сторонний сайт инициирует изменение | Средняя | Высокий | Strict SameSite, Origin и Fetch Metadata | CSRF token, связанный с серверной сессией, во всех mutation API | Низкий |
| Path traversal | Клиент подставляет путь к чужому файлу | Средняя | Критический | Строгие ID, кодовые roots, resolve/realpath | Использовать единый safe-files слой без абсолютных путей от клиента | Низкий |
| Symlink attack | Подмена файла ссылкой выводит чтение за root | Низкая–средняя | Критический | `lstat`, `realpath`, `O_NOFOLLOW` | Не допускать совместный write-доступ, integrity scan | Низкий |
| Массовая выгрузка | Сотрудник или атакующий экспортирует всё | Средняя | Критический | Полный экспорт без фильтра отклоняется | Preview, двойное подтверждение, step-up, TTL, аудит, лимиты | Средний |
| Инсайдер | Уполномоченный сотрудник злоупотребляет доступом | Средняя | Критический | RBAC и цепочка событий | Минимальные роли, регулярный пересмотр, двухлицевое подтверждение | Средний |
| Повреждение SQLite | Сбой диска/конкурентная запись делает индекс недоступным | Низкая–средняя | Средний | WAL, FULL sync, busy timeout, integrity check | Backup и проверенное восстановление; публичная форма не зависит от SQLite | Низкий для приёма, средний для кабинета |
| Потеря HMAC-ключа | Точный поиск старых контактов становится невозможен | Средняя | Средний | Версия ключа хранится с индексом | Реестр версий, защищённая резервная копия ключей, план ротации | Средний |
| Кража backup | Архив раскрывает все первичные данные | Средняя | Критический | Только архитектурное требование | Шифрование отдельным ключом, российская площадка, ACL, журнал, restore-test | Высокий до реализации backup |
| Раскрытие временного экспорта | ZIP доступен по URL или остаётся после TTL | Средняя | Критический | Путь вне public, интерфейс не реализован | Одноразовый контролируемый download, no-store, TTL, журнал, удаление | Средний |
| Formula injection | Значение из заявки исполняется в Excel/CSV | Средняя | Высокий | Нейтрализация `= + - @` | Применять ко всем табличным выгрузкам и тестировать | Низкий |
| Логирование ПДн | Ошибка или debug выводит контакты/тексты/пути | Средняя | Высокий | SafeSecurityLog и whitelist metadata | Запрет stack/path клиенту, ревью logger, тесты на секреты и ПДн | Низкий–средний |
| Ошибочное удаление | Просроченная запись удаляется вопреки основанию хранения | Средняя | Критический | Новая policy-модель; legacy `--apply` не изменён | Запрет legacy apply, human approval, legal hold, verify/report/audit | Высокий до worker Этапа 3 |
| Одновременный экспорт и удаление | Файлы исчезают во время сборки архива | Средняя | Высокий | `lead_operation_locks` и интерфейс lock service | DB/file lock, TTL блокировки, recovery зависших операций | Низкий после реализации worker |
| Повторная отправка заявки | Клиент не получает понятный ответ и создаёт дубли | Средняя | Средний | requestId, duplicate detection, сохранение при SMTP-сбое | Идемпотентность UI/API и безопасный статус stored | Низкий |
| Orphan-файлы | Заблокированное/оборванное вложение остаётся без заявки | Средняя | Средний | Индексатор обнаруживает orphan | Карантинный lifecycle и подтверждённое удаление с актом | Средний |
| Повреждённый JSON | Одна запись ломает индексирование всех заявок | Средняя | Средний | Bounded parser, finding вместо остановки | Очередь исправления, integrity report без содержимого | Низкий |
| Недоступность административной SQLite | Индекс не обновляется при новой заявке | Средняя | Низкий для клиента | SQLite не в критическом пути; JSON остаётся источником | Поздняя sync, обезличенный alert | Низкий |
| Компрометация секрета аудита | Атакующий пересчитывает цепочку событий | Низкая | Высокий | Ключ вне SQLite/Git | Разделить доступ, резервировать, периодически фиксировать внешний checkpoint | Средний |
| Публичная индексация кабинета | Робот или пользователь находит внутренний URL | Низкая | Высокий | Nginx 404, feature flag, robots, noindex, no-store | Сохранить изоляцию, не добавлять публичные ссылки/аналитику | Низкий |
| Небезопасное вложение | Менеджер скачивает blocked/not-configured файл | Средняя | Высокий | Карантин и antivirus status | Запрет роли MANAGER для blocked; предупреждение для not-configured | Средний до UI Этапа 3 |

## Приоритеты

1. До любого включения кабинета вручную закрыть внешний порт 3000.
2. Не запускать legacy cleanup `--apply`.
3. Не включать `PD_ADMIN_ENABLED` до проверки Node.js, каталогов, секретов, миграций и Nginx.
4. До официального экспорта реализовать step-up, approval, locks и TTL.
5. До заявления о резервном копировании реализовать шифрование и успешный restore-test.

## Проверка и ограничения цепочки аудита

`event_hash` — HMAC-SHA-256 от канонического представления разрешённых полей и `previous_hash`. Ключ хранится только в environment. `npm run pd:audit-verify` пересчитывает цепочку и обнаруживает изменение, удаление или перестановку известных записей. Механизм не является абсолютно неизменяемым: лицо, имеющее одновременно доступ к базе и ключу, может пересчитать цепочку. Для снижения этого остаточного риска нужен внешний периодический checkpoint и раздельные полномочия.
